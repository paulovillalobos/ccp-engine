# DECISIONS — why the contract looks the way it does

Each entry: the choice, why, and what it rules out. A change to schemas/ or to a core signature without a row here fails
the Monday audit (AUDIT.md). Numbered, never renumbered; superseded entries say so.

| # | Decision | Why | Rules out |
|---|---|---|---|
| D1 | Field names in English; identifier prefixes exactly as ARQUITECTURA.md §3 (`regra:`, `facto:`, `veredicto:`...); closed enumeration values in Portuguese: `cumpre / nao_cumpre / nao_avaliado`, reasons `facto_ausente, regra_ausente, cobertura_insuficiente, documento_sem_texto, conflito`, rule types `limiar, procedimento_admissivel, prazo_minimo, conteudo_obrigatorio, proibicao, agregada, seletor_regime, jurisdicao`, entity types `publica, privada, pessoa_singular` | Code and commits are English (handoff rule); the ids of §3 are already Portuguese and stable; the API (§9: `/v1/saude`, `/v1/verificar`) is read by Portuguese consumers, so the values they see are Portuguese. | D2 | Every stored object carries the envelope `id, revision, recorded_at, stale?, stale_reason?, supersedes?` (defs `envelope`). `recorded_at` is the record clock (when the revision entered the store). `known_at` and `valid_at` are domain clocks on `facto` and `veredicto` only; a fact's `known_at` equals the `captured_at` of its raw record (verify I08) | §7 names three clocks; the store needs a fourth, mechanical one to be append-only without touching the domain clocks. Making `known_at` universal would give norms and links a clock §7 does not define | A `known_at` on every object; overwriting a record in place |
| D3 | Store layout: `<store>/<type>/*.json` (one object) or `*.jsonl` (one per line), `<type>` = schema stem; `<store>/governance/{principals.json, events.jsonl}`; `<store>/raw_bytes/<sha256>`. Three stores: `fixtures/valid/`, the repository root (`law/`, `rules/`, `governance/`), and `data/` (extractor) | The extractor can start from the directory names alone; verify applies the same loader to all three; no database to install | A database schema; per-source layouts |
| D4 | A passage has `versions[]`, each keyed by `version` = its `valid_from` date, with `text`, the `raw` capture it came from and `offsets` of the text inside that capture's decoded bytes. A citation is `passage + version + quote + offsets`, offsets relative to the passage version's text (defs `citation`). DR notes are quoted with `raw_citation` (offsets in the raw capture) because they precede passages | Invariant 2 needs `text[start:end] == quote` to be checkable with no parser in the loop; keying by date makes `vigente(d)` a lookup | Quotes without offsets; citations to a passage id without a version |
| D5 | A rule id ends in `@v<n>` (its own version) and the record also has a store `revision` | `@v` changes when the legal content of the rule changes (new threshold, new passage); `revision` changes when the record changes (a reading added, a state replayed). | D6 | The eight rule types are one schema with `type` and a `params` object whose required keys depend on the type (`if/then`); conditions are data (`field, op, value, unit`). The engine never interprets text at run time; a missing field makes the rule `nao_avaliado / facto_ausente`, never false | §5 in code: adding a type is a schema change with a row here, not a new module; a condition on an absent fact must not silently fail | Rule logic in Python per rule; free-text conditions |
| D7 | `regra.readings[]` and `regra.state` are the replay of the governance log (each reading names its `evento`); the log is the source. verify I05: `state == settled` requires at least two readings of distinct `family`, one of them blind | Invariant 5 must be checkable on the stored rule without re-running the readers; the log remains the only writer | Editing a rule's state by hand |
| D8 | `agregada.params.completeness_threshold.decided_by` names an `evento` that must be an `approve` of a `product_rule` by a `human:` principal (verify I12). | D9 | An `entidade` may store `name` for any type (needed to link records); a `veredicto.entities[]` item of type `pessoa_singular` may not carry `name` (schema `if/then` + verify I11 on every publishable object) | Invariant 11 is about publication, not storage: without the name the parser cannot link a natural person's records | Dropping natural persons from the store |
| D10 | `manifesto` is its own schema, embedded by `$ref` in `veredicto.manifest`, with every list `minItems: 1`; `fixtures/valid/manifesto/` holds a standalone example | §7: a verdict must repeat months later; a manifest with an empty adapter or snapshot list cannot be replayed. verify I06 re-checks completeness | A manifest by reference (an id to look up) |
| D11 | `result == nao_avaliado` ⇔ `reason` non-null (schema `if/then`); `cumpre` / `nao_cumpre` require a `citation` and at least one fact in `facts_used` | Invariant 6; a positive verdict with no fact or no quote is exactly the false `cumpre` the system exists to avoid | `nao_avaliado` without a typed reason |
| D12 | Governance events: `approve` and `adjudicate` require `human:` (schema + replay); readings of the law (`assertion_type: regra`) are never human-approved and settle only by a blind `review/uphold` from a principal whose family differs from the proposer's; `product_rule` is an assertion type; a disputant never adjudicates their own dispute; principals carry `family` | Invariants 4, 5 and 12 and the rjue governance rules, re-stated for this domain.
