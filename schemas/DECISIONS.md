# DECISIONS — why the contract looks the way it does

Each entry: the choice, why, and what it rules out. A change to schemas/ or to a core signature without a row here fails
the Monday audit (AUDIT.md). Numbered, never renumbered; superseded entries say so.

| # | Decision | Why | Rules out |
|---|---|---|---|
| D1 | Field names in English; identifier prefixes exactly as ARQUITECTURA.md §3 (`regra:`, `facto:`, `veredicto:`...); closed enumeration values in Portuguese: `cumpre / nao_cumpre / nao_avaliado`, reasons `facto_ausente, regra_ausente, cobertura_insuficiente, documento_sem_texto, conflito`, rule types `limiar, procedimento_admissivel, prazo_minimo, conteudo_obrigatorio, proibicao, agregada, seletor_regime, jurisdicao`, entity types `publica, privada, pessoa_singular` | Code and commits are English (handoff rule); the ids of §3 are already Portuguese and stable; the API (§9: `/v1/saude`, `/v1/verificar`) is read by Portuguese consumers, so the values they see are Portuguese. The builder's prompt listed the reasons in Spanish (`hecho_ausente`, `regla_ausente`, `documento_sin_texto`, `conflicto`); they map one to one | A Spanish or mixed vocabulary in the API; translating ids |
| D2 | Every stored object carries the envelope `id, revision, recorded_at, stale?, stale_reason?, supersedes?` (defs `envelope`). `recorded_at` is the record clock (when the revision entered the store). `known_at` and `valid_at` are domain clocks on `facto` and `veredicto` only; a fact's `known_at` equals the `captured_at` of its raw record (verify I08) | §7 names three clocks; the store needs a fourth, mechanical one to be append-only without touching the domain clocks. Making `known_at` universal would give norms and links a clock §7 does not define | A `known_at` on every object; overwriting a record in place |
| D3 | Store layout: `<store>/<type>/*.json` (one object) or `*.jsonl` (one per line), `<type>` = schema stem; `<store>/governance/{principals.json, events.jsonl}`; `<store>/raw_bytes/<sha256>`. Three stores: `fixtures/valid/`, the repository root (`law/`, `rules/`, `governance/`), and `data/` (extractor) | The extractor can start from the directory names alone; verify applies the same loader to all three; no database to install | A database schema; per-source layouts |
| D4 | A passage has `versions[]`, each keyed by `version` = its `valid_from` date, with `text`, the `raw` capture it came from and `offsets` of the text inside that capture's decoded bytes. A citation is `passage + version + quote + offsets`, offsets relative to the passage version's text (defs `citation`). DR notes are quoted with `raw_citation` (offsets in the raw capture) because they precede passages | Invariant 2 needs `text[start:end] == quote` to be checkable with no parser in the loop; keying by date makes `vigente(d)` a lookup | Quotes without offsets; citations to a passage id without a version |
| D5 | A rule id ends in `@v<n>` (its own version) and the record also has a store `revision` | `@v` changes when the legal content of the rule changes (new threshold, new passage); `revision` changes when the record changes (a reading added, a state replayed). Verdicts name both (`rule.id`, `rule.revision`) | One counter for two kinds of change |
| D6 | The eight rule types are one schema with `type` and a `params` object whose required keys depend on the type (`if/then`); conditions are data (`field, op, value, unit`). The engine never interprets text at run time; a missing field makes the rule `nao_avaliado / facto_ausente`, never false | §5 in code: adding a type is a schema change with a row here, not a new module; a condition on an absent fact must not silently fail | Rule logic in Python per rule; free-text conditions |
| D7 | `regra.readings[]` and `regra.state` are the replay of the governance log (each reading names its `evento`); the log is the source. verify I05: `state == settled` requires at least two readings of distinct `family`, one of them blind | Invariant 5 must be checkable on the stored rule without re-running the readers; the log remains the only writer | Editing a rule's state by hand |
| D8 | `agregada.params.completeness_threshold.decided_by` names an `evento` that must be an `approve` of a `product_rule` by a `human:` principal (verify I12). Starting value 0.9 per month, as §12 recommends | Invariant 12: the threshold is a product decision and must be in the log as such, not a constant in code | A threshold constant in `engine/evaluate.py` |
| D9 | An `entidade` may store `name` for any type (needed to link records); a `veredicto.entities[]` item of type `pessoa_singular` may not carry `name` (schema `if/then` + verify I11 on every publishable object) | Invariant 11 is about publication, not storage: without the name the parser cannot link a natural person's records | Dropping natural persons from the store |
| D10 | `manifesto` is its own schema, embedded by `$ref` in `veredicto.manifest`, with every list `minItems: 1`; `fixtures/valid/manifesto/` holds a standalone example | §7: a verdict must repeat months later; a manifest with an empty adapter or snapshot list cannot be replayed. verify I06 re-checks completeness | A manifest by reference (an id to look up) |
| D11 | `result == nao_avaliado` ⇔ `reason` non-null (schema `if/then`); `cumpre` / `nao_cumpre` require a `citation` and at least one fact in `facts_used` | Invariant 6; a positive verdict with no fact or no quote is exactly the false `cumpre` the system exists to avoid | `nao_avaliado` without a typed reason |
| D12 | Governance events: `approve` and `adjudicate` require `human:` (schema + replay); readings of the law (`assertion_type: regra`) are never human-approved and settle only by a blind `review/uphold` from a principal whose family differs from the proposer's; `product_rule` is an assertion type; a disputant never adjudicates their own dispute; principals carry `family` | Invariants 4, 5 and 12 and the rjue governance rules, re-stated for this domain. The founder is not a legal authority; Reader B is the second family today, AMALIA the first | Human approval of a reading; a one-family settlement |
| D13 | Broken fixtures are overlays: `fixtures/broken/<name>/` mirrors the store layout and replaces or adds files over `fixtures/valid/`; `EXPECT` names the verify check code that must appear among the failures. Invariant 3 (no model in verify) cannot be a data overlay, so its fixture is a Python module under `engine_mutation/` that the import guard must refuse | One broken fixture per invariant, each tripping a named check; verify runs all of them and fails if any passes | Hand-maintained whole-store copies |
| D14 | `diff` is derived: by rule over `(id, revision)` of the two packages (`added / removed / changed`), by consumer field from the fields the changed rules reference (conditions, threshold, aggregate, deadline, selector, window anchor, group key). verify rebuilds it | §3 asks for a diff by rule and by consumer field; deriving it keeps it honest | A hand-written changelog |
| D15 | Unit ids: `<kind>:<source>:<id in source>` (`proc:base:FX-2026-000001`), colons allowed | The consumer identifiers of §9 are per source; the kind prefix is the only thing the engine needs | A global sequence; ids that hide the source |
| D16 | `raw.request.method` is the constant `GET` and `reads_of_page` is at most 1 (schema) | Invariant 10 as data on every capture; verify I10 checks it and the static guard checks the code | Capturing by form submission |
| D17 | Python 3.12; dependencies `jsonschema` (+ `referencing`) and `pytest` only; verify runs with `python -I` | The gate must be auditable by reading it; nothing in it resolves a `$ref` over the network | PDF or HTTP libraries in the gate |
| D18 | Fixture law texts are paraphrases marked `FIXTURE` on their first line; they have the shape of the law and are not the law | The scaffold must not contain a legal quote that was never captured and verified | Pasting real CCP text before B2 captures it |
| D19 | `valid_at` is a date; `known_at`, `recorded_at`, `captured_at`, `at` are UTC instants | A fact holds on a day in the world; a capture or a log entry happens at an instant | Mixed precision in one field |
| D20 | `pacote.hash = sha256(canonical(rules sorted by id))`; `log_head = sha256(canonical line of the last event)`; `prev` of an event = that same hash of the previous line; canonical JSON = sorted keys, no spaces, UTF-8 kept (engine/canon.py) | One hashing rule for the chain, the packages and the manifests; recomputable by anyone with the file | Per-module hashing conventions |
| D22 | Principals by role (product rule, Paulo, 2026-10-24): `pessoa:` (kind humano; decides product rules, approves with a reason, adjudicates), `leitor:a` / `leitor:b` (automatizado; propose readings by passage id; `familia` A or B; `motor` = technical engine id and version), `extrator:` (automatizado; proposes facts with position), `redator:` (automatizado; explains what is decided; records nothing), `ferramenta:<name>@<n>` (codigo; version; sha256 of its code, checked by verify PROV while not retired). Capabilities per role in `engine/governance.CAPABILITIES`. A `product_rule` proposed by a pessoa with a reason is settled on record | The role is what matters to the log, not the vendor; families are A and B so no model name reaches an id or a published output; a tool is a principal with a hash so a re-derivation names the exact code | Model names in ids; a builder principal; approval by anything automated |
| D23 | A raw record may carry `text`: the working text derived from its bytes by a versioned extractor (`engine/extract.py`, e.g. `dr-consolidated-fragments@1`), stored under `raw_bytes/<sha256 of the text>`; verify re-runs the extractor and requires the same bytes (I01); passage offsets point into the derived text, not into the HTML | The DR consolidated page is a rendered DOM; offsets into HTML would break on any re-render, offsets into a re-derivable text do not (rjue's NORMALISE layer) | Hand-edited working texts; offsets into HTML |
| D24 | Passage versions come from the per-article history view of the DR (full text of every previous version, each followed by the note that produced it), not from the amending acts; the consolidated page gives the current text and all notes (the `vigencia` records). Versions sharing a `valid_from` (a retificação and the act it corrects) are one legal version: the newest text wins and the earlier ones are kept under `rectified`. A note without "em vigor a partir de" (4 of 735) gets its date from the act's own entry-into-force article, recorded in the vigencia. The regime selector cites `dl-177-2026:art7.2` (Norma transitória) | Read on 2026-10-24 from the real pages: the history view carries the texts, so `vigente(d)` is a lookup, not a reconstruction; a rectification replaces text as of the same date, so a second version at the same date would be a false change | Reconstructing old texts from amending acts; one version per note |
| D39 | A rule file in rules/ is the replay of its latest propose/correct event in content: params, conditions and cited passage ids equal that event's payload (verify STATE, `check_rule_content`). Supersedes the union clause of D37: an unsettled rule cites only the proposer's passages; the reviewer's differing passages live in its review payload and in DESACORDOS.md. The leitores' raw answers are evidence anchored in the log: every event with `answer_sha256` must have its file under governance/readings/ hashing to it (READ). Measurement annotations and law/HELD-OUT.json are sealed by `tools/measure.py seal` (a `caso_referencia` event by `ferramenta:measure`, payload index_sha256 + held_out_sha256); verify SEAL refuses annotations without a seal or changed after it. The first held-out set (2026-10-24) was declared before any rule entered the log, which git shows (commit 4b518c21e before dca0342a6) and the first seal (evento:38) anchors from now on | The phase-3 audit changed a settled rule's threshold in rules/, edited a reader's answer and moved the held-out date, and verify passed all three: the replay was not compared with the log and the evidence files were not anchored | Rule content that differs from the log; unanchored answers; a held-out set that can be redrawn |
| D21 | Store directory names and schema stems coincide and `engine/schema.TYPES` lists them; `engine/schema.type_of(obj)` derives the type from the id prefix | The extractor writes `data/facts/facto/*.jsonl` and nothing else tells verify what it is; a file in the wrong directory fails | Type fields that can disagree with the directory |
| D25 | A manifest's (and a package's) `log_head` must be the head of **a prefix** of the governance log, and the last event of that prefix must not be after `manifest.produced_at`; it is not required to equal the current head (verify MAN).
